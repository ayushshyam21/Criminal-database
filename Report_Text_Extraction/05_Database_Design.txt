### Chapter 6: Database Design, ER & EER Modeling

Our database design changed substantially as the project matured. In DA1, Ojas Sugur proposed a preliminary 6-table concept (POLICE_STATION, CRIME, CRIMINAL, VICTIM, and bridge tables CRIMINALS_OF_CRIME and VICTIM_OF_CRIME). That initial design helped us model many-to-many relationships between suspects, victims, and offenses. However, when we started developing the web application, we realized that an operational police system must track internal station personnel, custody transfers, investigation notes, and public citizen submissions in distinct tables. This led us to develop our final 14-table BCNF schema.


### Enhanced Entity-Relationship (EER) Specialization

In the Enhanced Entity-Relationship (EER) model, police personnel exhibit Disjoint Total Specialization (d, t). All department members share foundational attributes like username, email, password hash, and active status, but they specialize into three mutually exclusive operational roles: Administrator, Police Officer, and Investigator. Rather than creating three separate child tables with identical columns, we used a Single Table with Type Discriminator pattern in users using MySQL ENUMs. This avoids unnecessary outer joins while preserving complete relational integrity.

### Complete Entity-Relationship Diagram (ERD)

The complete entity-relationship model spans 14 tables organized across four functional areas: the Police Operations Domain (police_stations, users, cases, persons, case_assignments, case_persons, evidence, investigation_notes), the Immutable Audit Domain (evidence_custody_log, audit_log), the Public Open Data Domain (iucr_codes, public_crime_incidents), and the Citizen Engagement Domain (citizens, citizen_reports). Foreign keys connect these tables to ensure that incidents, personnel, and evidence stay properly synchronized.

The formal relational schema for our 14 tables is detailed below. Primary keys are marked with [PK], alternate candidate keys with [CK], and foreign keys reference their respective parent tables:

10. AUDIT_LOG (log_id [PK], table_name, record_id, operation_type, old_values, new_values, performed_by, timestamp)

11. IUCR_CODES (iucr_code [PK], primary_type, description, fbi_code, is_active)

PUBLIC_CRIME_INCIDENTS (incident_id [PK], source_id [CK], case_number, incident_date, block, source_iucr_code, source_primary_type, source_description, canonical_iucr_code -> IUCR_CODES, location_description, arrest_made, domestic, beat, district, ward, community_area, fbi_code, latitude, longitude, incident_year, updated_on, imported_at)

### Chapter 8: Functional Dependencies & Normalization Proofs

A relational schema R is in Boyce-Codd Normal Form (BCNF) if and only if, for every non-trivial functional dependency X -> Y, the determinant X is a superkey of R. When developing our schema across DA1 and DA2, we systematically eliminated normalization anomalies: moving from unnormalized data to 1NF by ensuring atomic attributes; reaching 2NF by removing partial key dependencies; reaching 3NF by removing transitive dependencies; and finally verifying that every table satisfies BCNF.

Proof for USERS: The candidate keys for this table are {user_id}, {username}, {email}, and {badge_number}. Because every functional dependency in this relation has one of these candidate keys as its determinant, the relation satisfies BCNF.

Proof for CASES: The candidate keys are {case_id} and {case_number}. Every case attribute—such as title, category, priority, and classification level—is uniquely determined by these keys. Since both determinants are superkeys, the table satisfies BCNF.

Proof for CASE_ASSIGNMENTS & Virtual Constraints: In many police database designs, ensuring that an officer is assigned only once to an active case requires extra application-level validation checks. In our project, we solved this directly inside MySQL using virtual generated columns. The column active_assignment_key is defined as CASE WHEN is_active=TRUE THEN CONCAT(case_id, '-', user_id) ELSE NULL END. By defining a UNIQUE index on active_assignment_key, MySQL allows multiple historical rows (where is_active is false and the key is null) but strictly prohibits duplicate active assignments. The functional dependency {active_assignment_key} -> {assignment_id, assignment_role, notes} holds for all active rows, keeping the table in BCNF without relying on error-prone application code.
