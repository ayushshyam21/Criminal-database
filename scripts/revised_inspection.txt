P27: ABSTRACT
P28: Managing criminal case records in municipal police stations remains challenging when desks rely on paper diaries or unnormalized spreadsheets. These conventional workflows frequently suffer from duplicate entries, lost dossiers, lack of custody tracking, and dangerous database accounts that give full administrative control to regular web scripts. In this project, our team engineered the Criminal Case Management & Crime Analytics System (CCMS) to address these operational and data integrity issues. Built using Python Flask and MySQL Community Server 9.7 with the InnoDB storage engine, the system centers on a 14-table relational schema structured strictly to Boyce-Codd Normal Form (BCNF), backed by dynamic analytics rendered with Chart.js.
P29: The core database tracks the complete lifecycle of criminal investigations, linking incidents to suspect, victim, and witness profiles while tracking physical evidence through an immutable chain-of-custody ledger automated by database triggers. To allow public community engagement without risking internal police intelligence, we introduced a separate, decoupled Citizen Portal. Citizens can register securely, file non-emergency crime reports, and check progress using generated tracking codes (CR-YYYY-XXXXX). An anti-enumeration defense returning HTTP 404 Not Found prevents malicious probing of report numbers. We also integrated an ETL pipeline pulling over 50,000 public crime records from the City of Chicago open data portal, mapping them to standard Illinois Uniform Crime Reporting (IUCR) codes.
P30: System security combines a dual-account least-privilege database model with Bell-LaPadula Multi-Level Security across four tiers (PUBLIC, INTERNAL, CONFIDENTIAL, RESTRICTED) alongside discretionary Need-to-Know assignment checks. The web runtime account (crimedb_app) possesses zero schema alteration or deletion permissions on critical logs, while admin migrations run through crimedb_admin. We verified the implementation against our live MySQL instance with a 35-test automated Pytest suite and an end-to-end smoke test, achieving 100% pass rates. Secondary composite B-tree indexing reduced query row scans by over 95% on EXPLAIN benchmarks. The current system operates as an academic prototype, with future enhancements envisioned around spatial GIS indexing and biometric retrieval.
P31: Keywords: Criminal case management, relational databases, MySQL 9.7, Boyce-Codd Normal Form, Bell-LaPadula model, chain of custody, citizen portal, crime analytics, Python Flask, least privilege.

P02: Chapter 1: Problem Statement
P03: When handling criminal complaints, police stations must process a wide variety of incidents, from everyday theft and burglary to complex financial fraud, cyber-enabled phishing, and identity theft. In many local precincts and station desks, these complaints are still recorded by hand in paper general diaries or fragmented office spreadsheets. During our initial problem study in Digital Assignment 1 (DA1), we observed several recurring issues that undermine both data reliability and investigative speed in these traditional setups:
P04: 1.1 Manual Inefficiencies & Lost Records: Officers must handwrite complainant details, suspect descriptions, and stolen property logs repeatedly across different registers. If a physical FIR docket is misfiled or damaged by moisture, weeks of investigative progress can disappear before any forensic examination even begins.
P05: 1.2 Normalization Failures & Data Anomalies: Early computerization efforts often place officer ranks, station telephone numbers, and offense descriptions into every single incident row. This causes update anomalies whenever an officer is transferred, deletion anomalies when old complaints are purged, and insertion anomalies that prevent a newly joined officer from being registered in the system until they are assigned a case.
P06: 1.3 Tamperable Chain-of-Custody: In generic record management systems, evidence custody logs are typically stored in standard editable tables. A compromised station user or careless operator could change an evidence locker location, delete a transfer row, or modify confiscated amounts without leaving any permanent record of who made the alteration.
P07: 1.4 Over-Privileged Database Connections: Many student and small-scale web projects connect their application to MySQL using a single administrative user with blanket privileges (GRANT ALL). In that setup, any simple SQL injection bug or unhandled error can allow an unauthorized user to drop entire tables or read confidential dossiers.
P08: 1.5 Lack of Access Classification & Need-to-Know: In basic departmental software, any authenticated officer can freely search and view every case docket in the station. This breaks basic police protocols, because sensitive files—such as internal misconduct inquiries, homicide investigations, or informant reports—should only be accessible to officers with appropriate clearance who are actively assigned to that investigation.
P09: 1.6 Insecure Citizen Engagement: Victims who register complaints have no direct way to check their case status without visiting the station in person. On the other hand, exposing internal police database tables directly to a public submission form opens the door to SQL injection, spam data, and enumeration attacks where malicious users test sequential tracking numbers to discover private details.
P10: Chapter 2: Project Objectives & Scope
P11: To address these operational bottlenecks systematically, our team established seven concrete engineering objectives that shaped our database modeling and application architecture:
P12: 2.1 Relational Rigor (BCNF): Design and implement a 14-table relational schema that satisfies Boyce-Codd Normal Form across all tables, ensuring every non-trivial functional dependency relies on a candidate key as its determinant.
P13: 2.2 Security Clearance Hierarchy: Implement four hierarchical security clearance and classification levels (PUBLIC < INTERNAL < CONFIDENTIAL < RESTRICTED) based on the Bell-LaPadula Simple Security Property ("No Read Up"), paired with active assignment checks for operational Need-to-Know access.
P14: 2.3 Engine Privilege Isolation: Configure two dedicated MySQL database accounts: crimedb_admin for DDL migrations and trigger definitions, and crimedb_app for everyday web queries with zero DDL permissions, zero direct write access to custody and audit ledgers, and no delete rights on citizen accounts.
P15: 2.4 Public Service & Citizen Privacy: Create a separate citizen portal (/citizen/*) with independent session management, scrypt password hashing, automated tracking references (CR-YYYY-XXXXX), and an anti-enumeration HTTP 404 response to protect user privacy.
P16: 2.5 External Data Reconciliation: Integrate an automated ETL pipeline that pulls real public crime records from the City of Chicago Socrata Open Data Portal into public_crime_incidents, normalizing them against Illinois Uniform Crime Reporting (IUCR) lookup codes.
P17: 2.6 Server-Side Database Routines: Implement atomic stored procedures (sp_assign_case), deterministic stored functions (fn_case_duration), DEFINER audit triggers, analytical views, and declarative virtual generated columns directly within MySQL.
P18: 2.7 Performance Benchmarking: Construct composite secondary B-tree indexes for the most common search and filter queries, and evaluate query performance with MySQL EXPLAIN to measure the exact drop in examined rows.

P06: Functional Requirements Specification
P07: • FR-1 (Authentication & Password Security): The system must authenticate users securely using salted scrypt password hashing (scrypt:32768:8:1) for both internal police staff and external citizens.
P08: • FR-2 (Multi-Level Security Hierarchy): The application must restrict case visibility according to four clearance ranks: PUBLIC (1), INTERNAL (2), CONFIDENTIAL (3), and RESTRICTED (4).
P09: • FR-3 (Need-to-Know Verification): The backend must deny unassigned officers access to CONFIDENTIAL and RESTRICTED dossiers, returning HTTP 403 Forbidden on direct URL attempts.
P10: • FR-4 (Admin Staff Governance): Administrators must be able to view all personnel via /admin/staff, update their clearance tiers, and enable or disable staff logins.
P11: • FR-5 (Case Dossier CRUD): Authorized officers must be able to create, view, update, and manage the full lifecycle of cases, recording locations, priorities, categories, and closure dates.
P12: • FR-6 (Automated Assignment Routine): The system must execute sp_assign_case to manage investigator assignments atomically, ensuring exactly one active Lead Investigator per case.
P13: • FR-7 (Evidence Custody Ledger): Physical evidence items must be tracked with unique codes, and every change in storage location or custody must trigger an automatic, tamper-evident log entry.
P14: • FR-8 (Investigation Diary Notes): Assigned officers must be able to log dated investigation notes, with a confidentiality toggle that hides sensitive observations from unauthorized users.
P15: • FR-9 (Chicago Open Crimes Analytics): The application must provide interactive charts and filters for over 50,000 public records imported from the City of Chicago open data portal.
P16: • FR-10 (Citizen Portal Intake): Citizens must be able to register separately, submit non-emergency incident reports, and receive a formatted tracking code (CR-YYYY-XXXXX).
P17: • FR-11 (Anti-Enumeration Privacy Defense): When a logged-in citizen attempts to access a report filed by someone else, the system must return HTTP 404 Not Found to prevent ID enumeration.
P18: • FR-12 (SQL Evaluation Workbench): The internal portal must provide an interactive /sql-demo screen where faculty evaluators can execute queries, test views, call stored procedures, and inspect query plans.
P19: Chapter 5: System Design & Architecture
P20: Our web application uses a standard three-tier architecture that cleanly separates user presentation, application security logic, and physical database storage:
P21: Presentation Tier: Built using Bootstrap 5.3.3 and Chart.js 4.4.1 templates rendered by Flask's Jinja2 engine. Navigation bars adapt dynamically so officers only see links permitted by their clearance level. Citizens use a distinct interface theme with explicit disclaimers emphasizing that web submissions are for non-emergency reporting only.
P22: Application & Security Tier: Implemented in Python 3.14 using Flask 3.1.2. The security layer (security_service.py) enforces Bell-LaPadula clearance rules and Need-to-Know assignment checks before queries return records to the templates. Whenever an authenticated user executes an action, Flask sets MySQL session variables (@app_user_id, @app_username) on the database connection so that MySQL triggers know exactly who performed the change.
P23: Database Tier: Powered by MySQL Community Server 9.7 with the InnoDB storage engine. We chose InnoDB because it supports full ACID transactions, row-level locking, foreign key constraints with cascade behaviors, and virtual generated columns. Business rules and audit guarantees are anchored directly inside the database using check constraints, unique indexes, and DEFINER triggers.
P24: Dual-Account Least-Privilege Architecture
P25: During development, we deliberately avoided connecting the Flask application with an all-powerful root or administrative MySQL user. Instead, we established two distinct accounts with segregated responsibilities: an administrative user (crimedb_admin) for schema migrations and DEFINER trigger creation, and an application user (crimedb_app) used by the web service. The application user has no DDL permissions, cannot write directly to the custody or audit tables, and cannot delete citizen records.

P28: Bell-LaPadula Security Model & Discretionary Need-to-Know
P29: To stop officers from browsing sensitive files without authorization, we assigned integer ranks to our clearance levels: PUBLIC = 1, INTERNAL = 2, CONFIDENTIAL = 3, and RESTRICTED = 4. Under the Bell-LaPadula Simple Security Property ("No Read Up"), an officer u can only view a case o if Clearance(u) >= Classification(o). For cases marked CONFIDENTIAL or RESTRICTED, our security service also checks that the officer is either an Administrator, the original case creator, or currently assigned to the case in case_assignments. Rather than hiding links in the UI, this check is enforced directly in SQL via filter_cases_for_user(), so unauthorized cases never appear in query results, dashboard counts, or case lists.

P02: Chapter 6: Database Design, ER & EER Modeling
P03: Our database design changed substantially as the project matured. In DA1, Ojas Sugur proposed a preliminary 6-table concept (POLICE_STATION, CRIME, CRIMINAL, VICTIM, and bridge tables CRIMINALS_OF_CRIME and VICTIM_OF_CRIME). That initial design helped us model many-to-many relationships between suspects, victims, and offenses. However, when we started developing the web application, we realized that an operational police system must track internal station personnel, custody transfers, investigation notes, and public citizen submissions in distinct tables. This led us to develop our final 14-table BCNF schema.
P04: Enhanced Entity-Relationship (EER) Specialization
P05: In the Enhanced Entity-Relationship (EER) model, police personnel exhibit Disjoint Total Specialization (d, t). All department members share foundational attributes like username, email, password hash, and active status, but they specialize into three mutually exclusive operational roles: Administrator, Police Officer, and Investigator. Rather than creating three separate child tables with identical columns, we used a Single Table with Type Discriminator pattern in users using MySQL ENUMs. This avoids unnecessary outer joins while preserving complete relational integrity.

P12: Chapter 7: Relational Schema & Data Dictionary
P13: The formal relational schema for our 14 tables is detailed below. Primary keys are marked with [PK], alternate candidate keys with [CK], and foreign keys reference their respective parent tables:
P14: 1. POLICE_STATIONS (station_id [PK], station_name [CK], district_code [CK], address, phone, created_at)
P15: 2. USERS (user_id [PK], station_id -> POLICE_STATIONS, username [CK], email [CK], password_hash, role, clearance_level, full_name, badge_number [CK], is_active, created_at, updated_at)

P31: Chapter 8: Functional Dependencies & Normalization Proofs
P32: A relational schema R is in Boyce-Codd Normal Form (BCNF) if and only if, for every non-trivial functional dependency X -> Y, the determinant X is a superkey of R. When developing our schema across DA1 and DA2, we systematically eliminated normalization anomalies: moving from unnormalized data to 1NF by ensuring atomic attributes; reaching 2NF by removing partial key dependencies; reaching 3NF by removing transitive dependencies; and finally verifying that every table satisfies BCNF.
P33: Proof for USERS: The candidate keys for this table are {user_id}, {username}, {email}, and {badge_number}. Because every functional dependency in this relation has one of these candidate keys as its determinant, the relation satisfies BCNF.
P34: Proof for CASES: The candidate keys are {case_id} and {case_number}. Every case attribute—such as title, category, priority, and classification level—is uniquely determined by these keys. Since both determinants are superkeys, the table satisfies BCNF.
P35: Proof for CASE_ASSIGNMENTS & Virtual Constraints: In many police database designs, ensuring that an officer is assigned only once to an active case requires extra application-level validation checks. In our project, we solved this directly inside MySQL using virtual generated columns. The column active_assignment_key is defined as CASE WHEN is_active=TRUE THEN CONCAT(case_id, '-', user_id) ELSE NULL END. By defining a UNIQUE index on active_assignment_key, MySQL allows multiple historical rows (where is_active is false and the key is null) but strictly prohibits duplicate active assignments. The functional dependency {active_assignment_key} -> {assignment_id, assignment_role, notes} holds for all active rows, keeping the table in BCNF without relying on error-prone application code.

P11: EXPLAIN Benchmark Results
P12: We evaluated our indexing decisions by analyzing query execution plans with MySQL EXPLAIN before and after adding the indexes. Filtering public_crime_incidents by district ("001") and date range without an index forced MySQL into a full table scan (type: ALL) that checked all ~50,000 rows. P13: Chapter 14: Results & Discussion
P14: Designing, implementing, and testing our system provided several practical insights into database development and application security:
P15: 14.1 Relational Integrity in Practice: We found that enforcing integrity constraints directly in the database is much more dependable than relying only on web form validation. For example, our check constraint chk_cases_closure_consistency prevented cases from being marked "Closed" without a closing date, while virtual generated keys reliably blocked duplicate active assignments even during concurrent requests.
P16: 14.2 Least-Privilege Development Hurdles: Working with a least-privilege database account revealed practical challenges during test automation. In our citizen test suite, our cleanup code initially attempted to delete test accounts using crimedb_app, which immediately failed with MySQL Error 1142 because DELETE permissions were intentionally revoked. We solved this by generating unique UUID emails for test records instead of trying to delete them, which also served as proof that our database permissions were working properly.
P17: 14.3 Anti-Enumeration for Citizen Privacy: During initial prototyping, when a logged-in citizen requested another citizen's report, our endpoint returned HTTP 403 Forbidden. Although this blocked unauthorized access, it inadvertently confirmed that the requested report ID existed. We changed the response to HTTP 404 Not Found, eliminating the information leak and protecting citizens from automated tracking ID probing.
P18: 14.4 Template 404 Null-Safe Guards: During smoke testing, requesting invalid URLs caused template rendering crashes because Flask's request.endpoint was None on 404 pages. We fixed this by adding null checks ({% if request.endpoint and 'cases' in request.endpoint %}) across base.html, allowing custom error pages to display cleanly without triggering an unhandled 500 server error.
